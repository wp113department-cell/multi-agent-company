| Memory (past outcomes) | **NO — genuinely out of scope, schema limitation** | Investigated (read `app/memory/store.py::embed_task_outcome` in full): `memory_embeddings` task-outcome rows have **no `agent_name` field at all** — an outcome is attributed to a `task_id`/`epic_id`, and one epic's outcome is an aggregate across *multiple* dispatched agents (backend_dev, qa, reviewer), not attributable to a single agent's contribution. Reclassified from NO/PARTIAL → YES this pass: "Who decides which agents work," "Multiple agents work simultaneously (fan-out)" *(real, tested, opt-in)*, "Agents reject tasks they're not suited for," "Priorities managed," "Duplicate work prevented," "Experience (tenure)," "Confidence." **Real production crash fixed:** the 4 orphaned agent modules (`agent_roster_doc_agent`, `architecture_doc_agent`, `migration_guide_doc_agent`, `tool_catalog_doc_agent`) had real callers in `app/api/specialized_agents.py` and would have raised `FileNotFoundError` on first invocation — confirmed via `load_role()`'s source before writing the fix, not assumed. All 4 role files now exist, follow this repo's established doc-agent role-file pattern (verified against `roles/readme_agent.md`/`roles/api_docs_agent.md`/`roles/changelog_agent.md`), and load cleanly.

**Genuinely out of scope for this batch (new capabilities, not orchestration wiring gaps):**
1. **Dynamic subtask creation** — needs a new agent-facing tool (e.g. `propose_subtask`), a validated write path into `Subtask` from inside a worker agent's tool loop, and `run_manager()` re-polling for new subtasks mid-epic.
2. **Agent-to-agent delegation** (`delegate_to`/"call additional agents") — needs loop-prevention, cost/budget accounting, and an explicit security boundary on which agents may invoke which.
3. **Dynamic/mid-run tool-list switching** — needs a concrete, justified trigger design (when/why); building it without one risks contextless, unjustified logic.
4. **Memory-informed agent selection** — blocked on a real schema limitation: `memory_embeddings` task-outcome rows have no `agent_name` attribution (an outcome is per-task/epic, aggregating multiple dispatched agents), so wiring it into `select()` requires a schema change, not a wiring fix. Agent-level history is already captured via tenure/confidence/success_rate (fixed this pass).

**Production Enhancement Plan (for the genuinely-out-of-scope items above, for a FUTURE batch):**
- Dynamic subtask creation: design a `propose_subtask` tool (schema, approval semantics, who can call it), a `Subtask` insert path from a worker agent's tool handler, and a re-poll/refresh point in `run_manager()`'s wave loop.
- Agent delegation: design a `delegate_to` tool with an explicit allow-list per role (which agent may invoke which), a delegation-depth cap (loop prevention), and cost/budget propagation so a delegated sub-run counts against the same epic budget.
- Dynamic tool switching: define the real trigger conditions first (e.g. a reviewer-flagged issue category unlocking a specialized tool) before writing any code — this is a product decision, not an implementation detail.
- Memory-informed selection: add `agent_name` attribution to `memory_embeddings` task-outcome rows (schema migration), scoped per-agent within an epic's outcome rather than per-epic-aggregate, before `FleetManager.select()` (which would need to become async, or accept a pre-computed bias dict) can meaningfully read it.
