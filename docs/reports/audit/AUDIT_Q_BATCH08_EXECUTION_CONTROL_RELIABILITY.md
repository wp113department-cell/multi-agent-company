Returns the restored snapshot + publishes a `health_updated` audit event. Smoke-tested end to end: save → list → rollback → correct restored state. |
| Checkpoints | **YES** *(was PARTIAL — broader than assumed, but uneven)* | All three checkpointers are now Postgres-backed: (1) pipeline graph, (2) generic worker-agent graph (`run_agent_graph`, ~76 agents), and **(3) `chat_agent.py`** — previously the one gap (`MemorySaver()`, in-process only). | Recovery after crash | **PARTIAL** | Survives: DB rows, all three Postgres-backed checkpoint stores (now including chat). Still not real for (c) plain worker agents — the checkpoint exists (Postgres-backed) but, per the Recovery-after-reboot note above, no live resume-this-run caller exists or was safely buildable in this pass's scope. |

**§14 overall: substantially improved — 6 YES / 3 PARTIAL / 0 NO** (was 3 YES / 3 PARTIAL / 3 NO). Chat sessions — the interactive surface users spend the most time in — now have the same durable checkpointing as every other execution path, closing the "chat_agent is the architecturally separate, under-hardened path" pattern flagged in Batches 1 and 4. The one remaining structural gap (full cross-restart resume for worker-agent runs) is a real architectural decision, not an oversight — documented above with concrete evidence for why it's out of this pass's scope.

## §38 Failure Recovery

| Scenario | Verdict | Evidence |
|---|---|---|
| Docker crashes (sandbox) | **YES — fails closed correctly** | `SandboxUnavailableError` raised on Docker-unreachable, caught and turned into a `[SANDBOX UNAVAILABLE]` tool result rather than crashing the run or silently running unsandboxed. |

| Terminal/shell session closes | **YES** *(was PARTIAL — only handled at next app startup)* | New `start_bg_process_liveness_loop()` (`app/fleet/bg_process_registry.py`), wired into `app/main.py`'s lifespan as a plain `asyncio.create_task` (deliberately **not** leader-election-gated — the registry is a local JSON file tracking PIDs spawned by *this* host process, meaningless to another instance in a multi-instance deployment, unlike the DB-backed loops that mechanism protects). Runs every 60s while the app is up, checks every registered PID via `os.kill(pid, 0)`, reaps dead entries, and publishes a `health_updated` event — closing "nothing detects a closed shell while the app keeps running." `sweep_orphaned_processes()`'s startup-only sweep is unchanged and still the crash-recovery backstop. |
| VS Code / IDE closes | **N/A** | Not applicable — this is a web app, not an IDE extension. |
| Claude Code stops | **N/A** | Different product, not applicable. |
| Internet disconnects | **YES** *(was PARTIAL)* | Every production `anthropic.Anthropic()`/`AsyncAnthropic()` construction (`base_graph.py::_make_client`, `agents/base.py::_make_client`, `chat_agent.py::_client`, `versioned_memory.py`, `git_push_tool.py` ×2, `pipeline/bootstrap.py`) now passes explicit `max_retries=get_settings().llm_call_max_retries` instead of relying on the SDK's undocumented-here default. `tests/test_gap58_59_llm_outage_retry_and_breaker.py` (pre-existing, re-verified in this pass's full suite run) already proves — against the real `anthropic` SDK, not a mock — that this produces genuine exponential backoff with jitter (`0.5 * 2**n`, capped) on connection/408/409/429/5xx errors, and that the circuit breaker correctly counts one failure per fully-retried call, not per raw HTTP attempt. **Deliberately did not add a second, custom outer retry loop** — an initial version of this fix did, and it was reverted after checking it would duplicate the SDK's own already-proven mechanism and desync the breaker's tested failure-counting contract (`test_circuit_breaker_counts_one_failure_per_call_not_per_http_attempt`). |
| LLM API fails (rate limit/500/timeout) | **YES** *(was PARTIAL)* | Same evidence as above — real exponential backoff now explicit and consistently configured everywhere, on top of the existing circuit breaker (closed→open→half-open). |

**§38 overall: 4 YES / 1 PARTIAL / 2 N/A** (was 1 YES / 4 PARTIAL / 2 N/A). The LLM-connectivity findings turned out to already have real backing (the SDK's own retry, proven by a pre-existing test file this audit pass hadn't cross-referenced) — the fix was making that explicit and config-driven rather than an implicit, easily-disabled-by-accident default, not building new retry machinery.

**Remaining PARTIALs, and why they're honestly not YES:**
1. **Recovery after crash (§14)** — abort/resume flags and in-memory agent-health state are still lost on an actual process crash. This is inherent to being in-process state, not a bug; closing it fully would mean persisting per-run control-flow flags to the DB on every mutation, a much larger design change than this pass's scope.
2. **Recovery after reboot (§14)** — orphaned runs still get marked `failed`, not auto-resumed. Real forward progress shipped (trace_id linkage), full auto-resume is architecturally out of scope for this pass — see the concrete per-agent-graph-factory reasoning in the §14 table above.
3. **Continue from checkpoint if interrupted (§14)** — real for pipeline and chat now; still not real for plain worker-agent runs, same root cause as #2.

**What changed since the original pass (2026-08-07 remediation):**
1. Chat sessions moved from the one execution path without durable checkpointing to fully Postgres-backed, closing the "chat_agent is the architecturally separate, under-hardened path" pattern also seen in Batches 1 and 4.
2. Cancel is now a real, structurally-distinct terminal state — not just a label, but enforced via `resume_task`'s refusal to resume a terminal-status task.
3. Rollback has a real, manual, operator-invoked caller (dashboard-style API), matching this codebase's own established precedent for keeping judgment-call operations human-gated rather than force-auto-wiring them.
4. The default queue backend (asyncio) now shares RQ's wall-clock job timeout — the previously-inverted safety net is now present on both paths.
5. Disaster recovery tooling is now actually scheduled (systemd timer) and the core backend service auto-restarts — with a correction to the original plan's own migrate-service restart-policy suggestion.
6. DB statement timeouts, an explicit idempotency-key primitive, and a structurally-enforced transaction-boundary invariant close out every remaining §66 gap.
7. LLM retry/backoff findings turned out to already be real (proven by a pre-existing test file cross-referenced during this pass) — closed by making the SDK's own behavior explicit and consistently configured rather than building redundant custom retry logic.
