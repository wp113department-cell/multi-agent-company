## §15 Large Project Handling

| Checkpoint | Verdict | Evidence |
|---|---|---|
| Understand 9,000+ line files | **YES — genuinely well-engineered** | `read_file` checks against `file_fold_line_threshold` (default 1000). Non-code files fall back to bounded truncation with an explicit `[TRUNCATED]` marker. Tested against a real 9000+ line file (`test_gap60_61_scan_and_large_file_performance.py`). Unchanged this pass. |
| Edit very large files safely | **PARTIAL — architectural, out of pass scope** | `edit_file`'s exact-substring match preserves correctness regardless of file size, but there's no streaming — full file is loaded into memory on every read/write across every write-capable tool (`edit_file`, `write_file`, and their per-agent variants). Left as documented PARTIAL, consistent with this series' precedent (Batch 8) of not force-fitting deep cross-cutting rewrites into a single audit pass. |
| ~~Gap found: `read_files` (plural/batch) has no folding protection~~ **FIXED** | **YES** | `read_files` (`app/agents/tools.py:1383`) now applies the identical fold/truncate logic `read_file` already used — same `file_fold_enabled` / `file_fold_line_threshold` / `fold_file_content()` / fallback-truncation path, per file in the batch, with the same `[NOTE]`/`[TRUNCATED]` markers. A batch call including a 9,000-line file now folds it exactly like a single `read_file` call would, closing the inconsistency. Regression coverage: `TestReadFilesFoldingParity` in `test_audit_q_batch09_large_project_file_tech.py` (large-file folding, parity with `read_file`, small-file no-op). |
| Scan 1,000+ files | **YES** | No file-count cap; real incremental caching via SHA-256 content hashing (`known_hashes`), skipping unchanged files, genuinely wired into real callers (`api/repo.py`, `base_graph.py`, `mcp/server.py`) — not dead code. Unchanged this pass. |
| Modify 100+ files | **PARTIAL — architectural, out of pass scope** | Confirmed, consistent with Batch 1: only `rename_symbol` does unbounded multi-file writes in one call; no dedicated batch-edit tool exists. Building one is a new tool with its own conflict/atomicity semantics, not a bug fix in an existing tool — a scope decision left for a dedicated pass. |
| Build complete projects (scaffold) | **YES** | Real mechanism: `pipeline/bootstrap.py` detects a blank repo, runs `git_init`, has the architect agent produce a scaffold plan (`submit_scaffold_plan`), then the coder agent writes files and commits.
