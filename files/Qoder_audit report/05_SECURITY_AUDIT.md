## 2. Path & Command Policy Findings

### SEC-05-102 — Policy Engine v2 (DB-backed approval rules) is record-only: its gate functions have zero production call sites
- **Severity:** Medium · **File:** `backend/app/policy/engine_v2.py` · **Confidence:** High
- **Finding:** `engine_v2.py:1-5` documents itself as "Adds approval rules on top of the v1 hard-coded denylist… Rules live in the `policies` table so adding a rule = DB insert". In reality, the enforcement half of v2 — `check_file_against_policies` (59-82), `check_files_against_policies` (85-109), `has_approval` (112-131) — has **no production caller** (repo-wide grep: only `backend/tests/pending/test_manager_integration.py:128`). The only wired function is `record_approval` (`api/epics.py:356`, `POST /{epic_id}/policy-approval`, approver-gated). Nothing ever reads a recorded approval or blocks on a `blocking=True` policy match; an operator inserting a "blocking" policy row gets **no enforcement**.
- **Evidence:** engine_v2.py call-site grep (3 files total: epics.py:356, one pending test, `tests/test_policy_v2.py:7` which tests only `match_pattern_sync`). No write path (`base_graph._policy_check` at base_graph.py:1042-1102, handler guards) consults the `policies` table. Also, the unwired matchers compare the raw `file_path` against globs without normalization (`_glob_to_regex` 18-38; `regex.match(file_path)` 72) — `./secrets/x`, `secrets/../secrets/x`, or absolute paths would dodge any `*secrets*` rule if this were ever wired as-is.
- **Production impact:** a misleading control: the platform claims a configurable second approval layer that does not actually gate anything. No active bypass exists (the v1 hard denylist remains the enforced floor), but operators cannot rely on DB policies for anything except an audit trail of approvals.
- **Recommendation:** either wire `check_files_against_policies` + `has_approval` into the write chokepoint (`base_graph._policy_check`, before the v1 floor) with realpath/normalized paths and a "no approval ⇒ deny" behavior for blocking rules, or explicitly mark v2 gating as dormant-not-enforced in both the module docstring and the endpoint description. Effort: M.

### SEC-05-103 — Scoped-bash allowlists (`cat `/`head `) permit absolute-path reads outside the worktree when the sandbox is operator-disabled
- **Severity:** Low · **File:** `backend/app/agents/tools.py:1513-1529, 1795-1813, 1838-1856` · **Confidence:** High
- **Finding:** `_QA_ALLOWED_PREFIXES` includes `"cat "` (1524) and `"head "` (1525). The QA bash handler (1795-1813) validates only through `check_allowlisted_command` — which does correctly reject chaining metacharacters (see §7.4) — and never confines arguments to the worktree. With the default `BASH_SANDBOX_ENABLED=true`, execution is containerized (`tools.py:1802-1809` → `bash.py:178-194` → `run_sandboxed`, only `cwd` mounted), so `cat /etc/passwd` reads the container's own file — contained. With the **explicit operator opt-out** `BASH_SANDBOX_ENABLED=false`, `_run_bash_command_raw` runs on the host (`bash.py:196-213`, `subprocess.run(shell=True)`), so `cat /etc/passwd`, `cat ~/.ssh/config`, or any service-user-readable absolute path is returned into the model context. The devops variant shares the class (allowlist from `settings.devops_bash_allowlist`, config.py:430; handler tools.py:1838-1856).
- **Evidence:** tools.py:1513-1529 (prefix list), 1797 (allowlist-only check), bash.py:178-194 (sandbox branch) vs 196-213 (host branch, no containment on absolute paths); config.py:1178-1181 (`bash_sandbox_enabled` default True — so this is opt-out-mode only).
- **Production impact:** confined to deployments that explicitly disable the sandbox (documented escape hatch). Read-only exposure of host files readable by the service user; not a write/execution escalation. Low.
- **Recommendation:** for read-only prefixes (`cat `, `head `), reject absolute paths and `..` segments (or resolve and require containment under the worktree) independent of sandbox mode; keep the metachar rejection as-is. Effort: S.

### SEC-05-105 — `sandbox.py` module docstring understates the implemented rollout scope (stale, misled this audit's own scoping)
- **Severity:** Low · **File:** `backend/app/policy/sandbox.py:19-29` · **Confidence:** High
- **Finding:** the module docstring states the sandbox is "wired into the three fully-generic, denylist-only bash tools" and that "the other ~12 already-allowlist-scoped bash handlers (test-runner, dependency-audit, QA, devops, etc.) are intentionally NOT wired to this yet". The code contradicts this: `_run_bash_command_raw` routes **every** caller through `run_sandboxed` when `bash_sandbox_enabled` is True (default, config.py:1178), and the toolchain-needing variants explicitly pass a real toolchain image + per-variant network (bash.py:146-176; config.py:1243-1269) — directly observed in the QA (tools.py:1807-1808) and devops (1850-1851) handlers. This doc-vs-code contradiction caused an initial mis-scoping during this audit (an apparent "QA reads host files" issue that is actually contained by the default sandbox).
- **Production impact:** operators and future auditors reading the module docstring will believe most bash variants run unsandboxed and may skip prerequisite setup (`gridiron-bash-toolchain:latest` build, docker/bash-sandbox/Dockerfile) or mis-assess risk. Documentation-only; cross-flagged to audit 11 (same class as ORCH-04-106).
- **Recommendation:** update the docstring to the current rollout reality (denylist-only variants → minimal image; toolchain variants → toolchain image + documented network overrides; host fallback only on explicit opt-out). Effort: S.

## 3. Credential Handling Findings

### SEC-05-101 — Wrong/expired credential can hang a git clone unboundedly; the repo is left stuck in `cloning`
- **Severity:** Medium · **File:** `backend/app/api/repo.py:121-144`, `backend/app/services/git_service.py:230-260` · **Confidence:** High
- **Finding:** on a 401 from the remote, git consults `GIT_ASKPASS` **before** giving up; the app sets `GIT_TERMINAL_PROMPT=0` (git_service.py:217) but never neutralizes `GIT_ASKPASS`, and neither clone path can recover from a prompting askpass helper:
  1. `_clone_and_activate` awaits `proc.communicate()` with **no timeout whatsoever** (repo.py:144) — a hung clone pins the background task forever and leaves the `Repo` row in `status="cloning"` indefinitely.
  2. `_run_git`'s `asyncio.wait_for` timeout path (git_service.py:251-255) kills only the direct `git` child, then awaits a **second** `proc.communicate()` (254) — if grandchildren (`git-remote-http`, askpass) still hold the stdout/stderr pipe write ends, that await can never return (classic orphaned-pipe cancel gap). The baseline suite shows a test whose only bounded inner call is this 300 s path exceeding a 600 s pytest-timeout, consistent with this gap.
- **Evidence (live reproduction, 2026-10-02):** `pytest tests/test_b1_clone_security.py::test_wrong_token_fails_and_is_not_echoed` hangs reproducibly in isolation (45 s pytest-timeout fired; same test also hit the 600 s suite timeout at log lines 14763-14872 of `/tmp/qoder_full_suite.log`). Process tree at the hang: `git clone -- http://127.0.0.1:44529/repo.git …` (pid 67023) → `git remote-http`/`git-remote-http` (67024/67025) → `/bin/sh /usr/share/qoder-ide/resources/app/extensions/git/dist/askpass.sh "Password for 'http://127.0.0.1:44529'"` (67063) → `qoder-ide … askpass-main.js` (67066) — a GUI askpass that never answers in a headless context. `/proc/67023/environ` confirms `GIT_ASKPASS=/usr/share/qoder-ide/…/askpass.sh` + `VSCODE_GIT_ASKPASS_*` (injected by the IDE terminal session this suite ran in) alongside the app's own `GIT_TERMINAL_PROMPT=0`. In the background test (`test_background_clone_and_pull_use_env_credentials_not_url`, line 511), the captured log proves the hang point is exactly step 3 — the **wrong-token clone** — after two successful authenticated clones/pulls ("Repo cloned and activated" logged twice, then no further output until the timeout; log lines 14874-14878). The concurrency/infrastructure audit's run had the same 2 failures.
- **Production impact:** in any deployment whose service environment exports `GIT_ASKPASS`/a GUI credential helper (desktop-hosted dev instances, IDE terminals, some desktop credential managers), a user entering a wrong/expired PAT causes: clone background task pinned indefinitely, repo permanently `cloning`, no error message, no timeout, no retry. In a clean server environment (no askpass, no TTY) git fails fast — which is why CI does not catch this. Even in clean environments, defect 1 (no timeout in `_clone_and_activate`) and defect 2 (cancel gap in `_run_git`) leave credential-failure paths unbounded by design.
- **Recommendation:** (a) in the git env built by `_auth_env` and repo.py:111-115, also set `GIT_ASKPASS=/bin/true`, `SSH_ASKPASS=/bin/true`, and disable credential helpers (`GIT_CONFIG_COUNT` extend or `-c credential.helper=`), keeping `GIT_TERMINAL_PROMPT=0`; (b) wrap `_clone_and_activate`'s `communicate()` in `asyncio.wait_for` with a kill path that starts the process in its own session (`start_new_session=True`) and kills the whole process group (`os.killpg`) — applying the same process-group kill to `_run_git`'s timeout path (git_service.py:252-255) so grandchildren cannot hold the pipes; (c) on timeout set `Repo.status="error"` with a "clone timed out" message so the state is visible. Effort: S–M.

**Other credential-handling findings: none.** The vault, injection paths, redaction, and audit trails verified clean — see §7.6–§7.9.

## 5. Prompt Injection Resistance Assessment

**Verdict: adequate for the current tool surface; the enforcement boundary is the policy engine, not a heuristic — and that is verified to hold.**

- All tool results from content-capable tools (repo content, fetched pages, DB rows, memory entries) are wrapped in a forgery-safe "this is untrusted external data, not instructions" marker (`base_graph.py:2464-2482`; the wrapper neutralizes in-band delimiter forgery). The covered set is derived from `TOOL_MANIFEST` permission tags (`read_repo/network/read_db/read_memory`), not a hand-picked list, and bash is additionally flagged for injection-looking patterns (`_flag_suspicious_tool_output`, 2485-2498). 10 dedicated tests exist (`tests/test_phase63_prompt_injection_defense.py`) covering wrap/no-wrap, flag/no-flag, and common forged-message shapes.
- The chat agent's dangerous-command confirmation flow is **not** an evadable regex: `_is_dangerous_command` delegates to the same centralized `check_command` denylist (`tool_security.py:59-61`), and — critically — even if an LLM never calls the confirmed tool name or an attacker reframes the request, the call still passes through `_policy_check` at `chat_agent.py:4605` before `_execute_tool`, which applies `check_command` and protected-path rules and audit-logs denials. `run_parallel_commands` refuses dangerous subcommands outright (no confirmation channel exists there; 1908-1940), and one-shot handlers with no session fail closed (`BLOCKED`, chat handler 5170-5235).
- Residual risk, stated honestly: the wrap/flag layer is advisory (content is preserved, not rejected — deliberate, to avoid losing real content), so a successful injection can still *persuade* an agent; containment is the deny-by-default policy engine + worktree containment + sandbox, which the test suite and this audit's sweeps verify. Agents with the broadest read access (research/docs/chat reading arbitrary repo files) do not possess write/execute tool scopes beyond the globally-policed set.

## 7. Confirmed Safe (with evidence)

1. **Path denylist is real (not documentation):** `engine.py:78-109` `_matches_path_rule` blocks `.env`/`.env.*`, any `secrets/` path segment + `secrets` regex, `*.pem/key/pfx/p12`, `id_rsa*` family, `.github/workflows/**` (both segments must appear — a single-segment check was the historical bug), `.git/**`. Exercised by `tests/test_policy.py` — **28 tests, 0 failures** in the baseline run.
2. **Worktree containment for every write-capable tool:** `check_path_in_worktree` (engine.py:121-141) is realpath-based (symlink-escape safe). Sweep of all write sites: coder `write_file`/`edit_file` (tools.py:1711, 1744), all `app/tools/filesystem/*` handlers via `_is_protected_path(rel, worktree_path)` (e.g. delete_file.py:97), staging/apply handlers, cleanup/schema/ai-engineer writers — every `write_text` site has a nearby containment guard; QA/reviewer are read-only by handler construction.
3. **Command denylist enforced at the chokepoint, for both graphs:** `base_graph._policy_check` (1042-1102) runs `check_command` for bash/execute-type tools and applies the path denylist to extracted patch targets; called at base_graph.py:2766 (fleet execute_tools) **and** chat_agent.py:4605 (before `_execute_tool`, with `audit_log` policy-denial recording). ~60 patterns (engine.py:189-250) include `rm -rf` variants, `git push`, `kubectl`, `docker push`/mutating docker subcommands, cloud deploy CLIs, `npm publish`, raw `curl`/`wget` URL, `sudo`, reverse shells; `_normalize_command` (149-165) strips quotes so `r''m -rf` is still caught; `_NON_OVERRIDABLE_PATTERNS` (175-183: `rm -rf`, `dd if=`, `mkfs`, `shutdown/reboot`, fork bomb, `>/dev/sd*`) hard-deny even with human override (`is_command_override_eligible`, 284-295).
4. **Allowlist prefix matching is injection-resistant:** `check_allowlisted_command` (engine.py:298-318) rejects `; && || | (single) backtick $( ) > < \r \n` **before** the prefix check (regex at 252) — the brief's QA-chaining-bypass question is answered: not bypassable. QA/test-runner/refactor/migration suites are additionally protected by the denser `check_command` in the shared chokepoint.
5. **`cd`-escape boundary check** for coder bash (engine.py:333-370, wired tools.py:1728-1730 — SEC-05-005 fix verified).
6. **Credential vault:** Fernet encryption with `enc:v1:` prefix + explicit legacy-plaintext passthrough (one-time warning); `ProjectCredentials` is frozen with `SecretStr` fields and field serializers that emit `**********` unless `context={"expose_secrets": True}` is explicitly passed; `get_env_vars()` (credential_vault.py:151-160) is the single raw-value extraction point; production requires `CREDENTIAL_ENCRYPTION_KEY` (config.py:1981-1995) and validates it as a real Fernet key (1963-1979).
7. **Reserved credential names:** `_RESERVED_SECRET_NAMES` (settings.py, SEC-05-011 fix) blocks storing `DATABASE_URL`, `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, JWT/encryption keys, `DEFAULT_ADMIN_PASSWORD`, AWS keys etc. as custom secrets; `list_custom_secrets` returns names only.
8. **Injection paths are minimal and named-only:** `GITHUB_TOKEN`/`ANTHROPIC_API_KEY` are popped from custom secrets before `extra_env` reaches any agent (agents.py:528-533; ~944-956). Host-mode bash env drops all secret-looking variable names (`bash.py:101-117`) and re-adds only explicit `extra_env`; `extra_env` values are masked as `[REDACTED]` in returned and streamed output (`bash.py:120-128, 245-250`); the chat graph redacts provider secrets from tool results (`chat_agent.py:4677`). Git tokens never touch argv or the persisted remote (git_service.py:207-218; verified by `test_b1_clone_security.py`'s on-disk/argv assertions — those tests' *backend* logic is sound; their hang is SEC-05-101).

10. **Sandbox is real, default-on, and fail-closed:** fresh `--rm` container per command, unique name + explicit `docker kill` on timeout, `--read-only` root + capped tmpfs `/tmp`, non-root host UID/GID, memory/pids/cpus caps, only `cwd` mounted at `/workspace` (`ro` for SCAN agents), no docker.sock; `SandboxUnavailableError` when Docker is unreachable — never a silent unsandboxed fallback (sandbox.py:96-247; config default `bash_sandbox_enabled=True` config.py:1178-1181). The variant network overrides (`network=host` for test-runner/qa/refactor/migration, config.py:1261-1269) are a documented, evidence-driven exception for loopback-bound Postgres.
11. **AuthN/AuthZ:** see §4 (75-route sweep, require_approver on every approval endpoint, deny-by-default RBAC, production auth validators, CORS default not `*`, admin seeded once with forced password change).
12. **Prompt injection:** see §5 (manifest-derived wrap/flag sets, 10 tests, denylist-backed confirmation, chokepoint enforcement, fail-closed one-shot contexts).
13. **Supply chain gates exist and are blocking:** `pip-audit` (ci.yml:328-346, suppression removed per SEC-05-019), `pnpm audit` (227-241, blocking per production-hardening pass), eslint without `|| true` (246-253, INFRA-06-004), plus a regression-gate step and Windows/e2e jobs; `requirements.txt` fully pinned with a documented reason for the one remaining `--ignore-vuln`.
